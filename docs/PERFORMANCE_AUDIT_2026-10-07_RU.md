## Подтверждённые узкие места

### 1. Оригиналы остаются в RAM у неактивных холстов

`hooks/useFullSizeImageCache.ts:6` хранит data URL оригиналов в React state без лимита памяти или LRU. `contexts/app-context/useSessionSyncAndAutosave.ts` сохраняет этот кэш в `tab.state.fullSizeImageCache` при синхронизации и переключении холстов. `hooks/useTabs.ts:472` держит массив холстов в памяти.

Смена активного кэша не освобождает старый, поскольку на него продолжает ссылаться состояние другого холста. Не обязательно происходит физическое копирование каждой строки: несколько ссылок могут удерживать один объект. Но сериализация создаёт отдельное представление данных, и сборщик мусора не освобождает достижимые оригиналы.

`utils/imageMemoryCache.ts` содержит отдельный Map, однако поиск импортов показал использование только функций очистки в useTabs и useSessionSyncAndAutosave. Это не действующий механизм управления основным React-кэшем; его изменение само по себе проблему не решит.

**Предложение:** единое хранилище media assets вне React; в ноде — assetId, размеры, MIME и ссылки на производные preview. Оригинальные байты сохранять на диск/IndexedDB до разрешения выгрузки. В памяти оставлять только необходимые для текущей операции оригиналы и видимые preview.

### 2. Оригиналы сериализуются вместе с настройками нод

`components/nodes/image-input/types.ts` определяет `ImageBatchItem.dataUrl`; `useImageInputBatch.ts:142` добавляет оригинал, а строки 181–186 передают весь batchFiles в значение ноды. `ImageInputNode.tsx:100` сериализует обновлённое значение.

`components/nodes/batch-prepare/hooks/useBatchPrepareStateAndInputs.ts:143` строит fullExport с packs, activeViews, multiview, extractedImages и image. Одни и те же активные изображения попадают в несколько полей JSON. `:167` сериализует весь объект при обновлении.

`components/nodes/ImageEditorNode.tsx:37,62` также использует parse/stringify значения, хотя локальные входы там уже отделены от оригиналов и имеют preview 256 px. Нельзя переносить вывод о хранении всех оригиналов в value одинаково на все типы нод.

**Предложение:** заменить изображения на assetId, отделить настройки и статусы от бинарных данных, производные downstream-поля вычислять по ссылкам. Нужна миграция старых проектов и адаптация всех читателей: генерации, цепочек, каталогов, copy/paste, экспортов, detached windows и recovery.

### 3. Batch Manager eagerly загружает архивы при старте

`hooks/batch-manager/useBatchStorageAndRestore.ts:94–114` проходит по initialJobs, читает архивы и возвращает items с изображениями и rawJsonl в batchJobs state. Запись metadata в localStorage удаляет большие поля (`:63–68`), но возвращаемое состояние next содержит их полностью.

**Предложение:** стартовать только с metadata, читать архив по явному запросу просмотра/вставки/скачивания. После завершения операции освобождать payload. Учитывать настроенные автоматическую вставку и восстановление карточек: они могут требовать загрузки, но только нужных заданий. Для крупных заданий перейти от чтения всего JSON-архива к отдельным asset-файлам и manifest с индексом.

### 4. Image Input удерживает ZIP и распакованные данные результатов

`components/nodes/image-input/hooks/useImageInputBatch.ts:652–666` создаёт ZIP Blob и кладёт его вместе с generatedFolders в batchResult. `types.ts` показывает dataUrl файлов внутри folders. Повторное скачивание использует сохранённый zipBlob (`:696`). Revoke временного download URL не очищает batchResult.

Это удержание до очистки состояния/размонтирования, а не доказанная бессрочная утечка. Во время обработки также одновременно существуют источники, результаты и структуры JSZip.

**Предложение:** после успешного сохранения архива держать archiveId/path, имя, счётчики и manifest. Повторное скачивание читает готовый архив; просмотр отдельного файла читает один asset. На Electron выполнять запись/архивацию потоково в background worker; для web — Worker и IndexedDB с ограниченной очередью. Перенос только ZIP в Worker не освобождает исходные data URL, если UI продолжает хранить их.

### 5. Miniature-компонент может сначала декодировать исходник

`components/nodes/image-editor/OptimizedThumbnail.tsx:96–99` устанавливает исходный src до получения thumbnail. Одновременно createCachedThumbnail создаёт Image, рисует canvas и вызывает синхронный toDataURL. При большом исходнике это может вызвать всплеск декодирования; во многих AI Editor slots src уже является preview, поэтому размер всплеска зависит от пути загрузки.

Кэш ограничен количеством 1000, а не байтами. Ключ из первых 80 символов и длины не гарантирует уникальность. Нет общей очереди, отмены Image-загрузки и объединения одинаковых незавершённых запросов. Cleanup предотвращает setState после unmount, но саму обработку не отменяет.

**Предложение:** готовые preview при импорте/получении результата, placeholder до готовности, ключ assetId + revision + размер, объединение запросов, приоритет видимых элементов, ограничение параллелизма. Хранить производные Blob и URL с контролируемым сроком жизни. Сохранить прозрачность для изображений, где она значима; нынешний JPEG-превью не подходит для всех материалов.

### 6. MultiView отображает оба списка целиком

`components/nodes/prompt-sequence/MultiviewSequenceView.tsx:612,772` использует items.map в обеих колонках, `:642,835` — обычные img без loading/decoding. Локальный импорт делает 512 px preview (`:191`), upstream-входы могут иметь другой размер. Одна карточка может одновременно присутствовать в двух колонках вместе с textarea и обработчиками.

**Предложение:** виртуализация обеих колонок, отдельный memo-компонент карточки, preview 64/128 для списка и более крупный preview только в открытой карточке. Размеры выбирать с учётом масштаба и DPR. Сохранять несохранённый текст и фокус при уходе строки из виртуального окна. `image` сейчас используется также как источник для AI-анализа — уменьшать его глобально нельзя: UI-preview должен быть отдельным полем.

`image-editor/SequencedPromptList.tsx:66` тоже создаёт список всех выбранных кадров. visibleIndices там — фильтр выбора, а не отсечение по viewport. Виртуализация полезна и здесь, особенно при больших последовательностях; scrollToIndex потребуется адаптировать.

### 7. Общий Context распространяет обновления по интерфейсу

`contexts/AppContext.tsx:665` объединяет данные холста, globalState, историю, очередь, batchManager и другие hooks в один Provider. `components/NodeView.tsx:52` и OutputPanel подписаны на этот Context; React.memo не предотвращает обновление из потребляемого Context.

`useFullSizeImageCache.ts:18` меняет identity getter при каждом обновлении кэша. Это сейчас обеспечивает инвалидацию данных. `hooks/useDerivedMemo.ts:134` на изменение getter или любого node.value очищает общие derived-кэши; изменение одной ноды может затронуть многие downstream-вычисления.

**Предложение:** отдельные подписки по nodeId/assetId, независимый viewTransform/interaction state, стабильные команды и адресная инвалидация по revision и зависимостям графа. Просто убрать getter из dependencies нельзя: это создаст устаревшие результаты. Сначала заменить механизм уведомления.

### 8. История и сохранение загружают/переносят большие payload

`hooks/useGenerationHistory.ts:64` читает всю историю getAll, кладёт записи с url оригиналов в state и параллельно достраивает отсутствующие preview. Лимит по умолчанию 100 не исключает значительную память, особенно при data URL. Закрытие панели не освобождает глобальный history state.

`hooks/useTabs.ts:44–76` сохраняет весь sessionObj с холстами через Electron и IndexedDB. LocalStorage fallback исключает fullSizeImageCache, но это не убирает оригиналы внутри node.value у Image Input/Batch Prepare. `useSessionSyncAndAutosave` вызывает saveSessionToDB также при переключении холстов.

**Предложение:** история — metadata и thumbnail с cursor/pagination, оригинал по запросу. Сессии — manifest ссылок, сохранение только изменённых метаданных и новых assets; координация всех путей save, а не только таймера. Сохранять прежнюю надёжность восстановления, версионирование и переносимость экспорта проекта.

## Политика памяти

Разделять три уровня: оригинальные байты на постоянном носителе; сжатые preview/Blob в ограниченном RAM-кэше; декодированные изображения/bitmap и DOM только для видимой области.

| Состояние | Что держать в памяти | Когда выгружать |
| --- | --- | --- |
| Видимые карточки | Preview нужного размера и небольшой запас | После выхода за запас и короткого grace period |
| Активное редактирование/просмотр | Нужный оригинал или editing bitmap | После закрытия и завершения операции |
| Свёрнутая/невидимая нода | Метаданные; при необходимости небольшое preview | Освободить тяжёлые UI-ресурсы, не трогать выполняющуюся задачу |
| Другой холст | Метаданные графа и screenshot вкладки | Оригиналы и крупные preview освободить после durable write |
| Архив завершённого batch | Metadata и manifest | Payload только на время чтения/вставки/экспорта |
| Задача генерации/нарезки | Только используемые входы/выходы | Освободить после этапа/завершения/отмены |

LRU должен учитывать байты и активных потребителей, а не только количество картинок. Стартовые экспериментальные настройки: 2–4 задачи подготовки изображений одновременно, overscan 1–2 ряда, grace period около 1–3 секунд. Конкретный бюджет RAM подобрать по замерам; это не проверенные оптимальные значения.

Blob URL не заменяет постоянное хранилище: он удерживает Blob и требует revoke после освобождения последним потребителем. ImageBitmap требует close; canvas — сброса/освобождения backing buffer. Управлять всеми этими ресурсами через общий lease/refcount. Browser/GPU allocator может не вернуть память ОС мгновенно, поэтому проверять также отсутствие удерживающих ссылок и повторное использование памяти.

Для ориентирования: RGBA-буфер 1024×1024 занимает 4 MiB, 2048×2048 — 16 MiB, 4096×4096 — 64 MiB. 30 таких буферов — 120/480/1920 MiB соответственно. Это арифметическая оценка одного уровня декодирования, не измерение приложения и не предположение, что все картинки сейчас декодированы одновременно. Размер PNG/JPEG на диске не отражает размер такого буфера.

## Обязательные ограничения реализации

1. Не удалять оригинал из единственного места хранения. Данные сохранять атомарно до выгрузки и проверять успешность записи.
2. Сейчас getter синхронный; многие пути используют `original || thumbnail`. После LRU eviction это может незаметно отправить миниатюру в генерацию/экспорт. Нужен async acquireOriginal(assetId) с загрузкой и явной ошибкой, без подмены оригинала preview.
3. Долгие операции должны жить в task service, отдельно от визуального компонента: существующее отсечение viewport уже может размонтировать его. Image Input processing и MultiView имеют локальные state/ref; перед дополнительным размонтированием проверить выполнение, отмену и обновление неактивного холста.
4. Сохранить байты, MIME, альфа-канал, привязку кадров и порядок A/B. Preview можно перекодировать, оригинал — только по отдельной операции пользователя.
5. Удаление с диска — отдельная сборка мусора по ссылкам проектов, каталогов, истории, задач, recovery, удалённых нод и открытых окон. Выгрузка из RAM не должна вызывать clearUnusedBatchArchives.
6. Detached/docked windows — самостоятельные потребители; освобождение ресурса одним окном не должно ломать остальные.

## Рекомендуемый порядок работ

1. Создать воспроизводимый fixture и записать baseline: ниже приведена матрица проверок.
2. Убрать стартовую hydration всех архивов; хранить ZIP результатов вне UI state; исправить fallback и очередь thumbnails; виртуализировать MultiView и SequencedPromptList. Проверять локальный state при unmount. Архивы на диске уже есть, поэтому часть работ не требует полного переустройства приложения.
3. Ввести AssetStore и миграцию оригиналов из node.value, fullSizeImageCache, batchJobs и history в persistent assets; сохранить совместимость проектов и API-потребителей.
4. Добавить ограниченный кэш, leases, viewport-выгрузку и выгрузку неактивного холста. Без шага 3 полноценная безопасная выгрузка оригиналов невозможна.
5. Разделить Context/подписки, сделать адресную инвалидацию derived data и облегчить сохранение. Тяжёлую нарезку, превью и ZIP выполнять вне UI-thread с backpressure.
6. По trace проверить вторичные затраты: раскладку и ResizeObserver при resize, обновления scroll/pointer/viewTransform, обработчики и SVG-связи, тени/анимации. Объединять обновления через requestAnimationFrame там, где trace подтверждает пользу. Не отключать эффекты вслепую.

## Проверка результата

- Fixture: 30 изображений 2K и 4K, перечисленные четыре типа нод, минимум три холста, заполненные история и завершённые batch jobs. Использовать реальные размеры и форматы пользователя, включая PNG с прозрачностью.
- Записать React commits и render durations, Chrome Performance long tasks, frame times p50/p95 и input latency; JS heap, renderer/main working set и доступные GPU-метрики отдельно. Heap snapshot до/после GC использовать только для диагностики удерживающих ссылок, а не как пользовательский механизм очистки.
- Сценарии: импорт; панорамирование и zoom; внутренний scroll; редактирование одного prompt; resize; сворачивание; уход ноды за экран; 10 переключений холстов; экспорт ZIP и повторное скачивание; перезапуск.
- Проверить переходы во время активной генерации/нарезки: задача продолжает работать, отмена доступна, результат попадает в правильную ноду/холст. Проверить восстановление и старые проекты.
- Убедиться, что изменение одной карточки не обновляет весь граф, старт не гидратирует все архивы, память после прогрева и повторений выходит на плато, а число DOM-карточек ограничено viewport.
- Сравнить хэш оригинальных байтов до/после выгрузки и восстановления; проверить downstream-генерацию, нарезку, export, copy/paste, viewer и detached windows.
- Цель для взаимодействий на тестовой машине: кадры около 16,7 ms при 60 Hz и отсутствие регулярно повторяющихся задач UI-thread свыше 50 ms. Это критерии для проверки, не обещание уже достигнутого результата.

Проверки выполнять на установленном Electron-приложении пользователя, а не только в Vite dev: результаты и стоимость работы различаются.
